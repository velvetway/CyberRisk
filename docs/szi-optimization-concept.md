# Подбор оптимального комплекса СЗИ: идеи к обсуждению

Черновик для оценки. Не план работ — набор идей и развилок, по которым нужно твоё решение.

Задача из постановки:

1. Анализ отдельных средств защиты внутри класса, комплекса мер и их совместимости, со стоимостью и эффективностью.
2. Подбор оптимального комплекса на дистанции (стоимость и эффективность).

---

## 1. Что уже есть

Прежде чем строить новое — инвентаризация. Я прошёл по коду и БД.

### Модель риска работает и она уже мультипликативная

[calculate](../internal/service/ptszi/service.go#L173) считает:

```
W = (Q_threat + Q_severity + (1 − Q_reaction)) / 3 · Z
```

Самое ценное для нашей задачи — `Q_reaction` ([service.go:207](../internal/service/ptszi/service.go#L207)):

```
покрытие звена VL_i = 1 − ∏(1 − coverage_j · effectiveness_j)   по внедрённым мерам j
Q_reaction          = среднее покрытие по всем VL угрозы
```

Это **уже не линейная сумма**, а вероятностная модель «хотя бы одна мера сработала». Значит фундамент для оценки комплекса заложен: две меры на одном звене дают убывающую отдачу, а не удвоение. Это ровно та нелинейность, из-за которой задача выбора становится интересной.

### Что умеет выдавать сейчас

`missingControls` + `recommendationsFromMissing` ([service.go:229](../internal/service/ptszi/service.go#L229)) — перечисляют, каких мер нет, с приоритетом из `switch` по коду. Это **список**, а не выбор: без стоимости, без сравнения вариантов, без учёта того, что бюджет конечен.

### Сверка с концепцией из презентации

Прошёл по `как работает.pdf` и проверил каждый коэффициент по живой базе. **Реализация соответствует концепции** — расхождений в ПТСЗИ-контуре нет.

| Что в концепции | Как в коде | Статус |
|---|---|---|
| `Z = 1`, если угроза актуальна для обоих контуров, иначе `0.5` | [zFromContours](../internal/repository/ptszi_repository.go#L503) — ровно так | ✅ |
| Потенциал нарушителя → `Q_threat`: низкий 0.33, средний 0.66, высокий 1 | 123 УБИ → 0.33, 83 → 0.66, 19 → 1.00 | ✅ |
| Число нарушенных свойств CIA → `q_threat`: 1→0.33, 2→0.66, 3→1 | 88 / 53 / 86 записей соответственно | ✅ |
| Коэффициенты `ST` из выгрузки БДУ | миграция `015` пересчитывает их как среднее по связанным УБИ | ✅ |

Два наблюдения, которые стоит знать (не ошибки, но влияют на точность):

- **2 УБИ имеют потенциал `unknown` → 0.50** — значения вне шкалы 0.33/0.66/1. На фоне 227 записей роли не играет.
- **Число УБИ за угрозой очень неравномерно**: `ST2` опирается на 170 УБИ, а `ST6` — всего на 4, `ST8` — на 7. Среднее по четырём записям куда менее устойчиво, чем по ста семидесяти. Для оптимизации это значит, что коэффициенты разных `ST` имеют разную надёжность — довод в пользу анализа чувствительности из раздела 6.

Отдельно: **в старом risk-калькуляторе `Z` считается иначе.** [ZFromAsset](../internal/service/risk/calculator_v2.go#L58) берёт его из среды актива (`prod` → 1.0, `stage` → **0.75**, `dev` → 0.5, изолированный → 0.5). Значения `0.75` в концепции нет вообще, и смысл другой: там `Z` про контуры угрозы, здесь — про окружение актива. Это вторая, параллельная линия расчёта; ПТСЗИ-контур её не использует. Раз существующее не трогаем — просто помним, что в проекте живут две разные трактовки `Z`, и на защите лучше показывать ту, что в `ptszi_repository.go`.

### Чего нет вообще

Проверил поиском по всему репозиторию — ни одного упоминания:

- **стоимости** в любом виде: ни закупки, ни владения, ни трудозатрат;
- **продуктов** как сущности БД — конкретные СЗИ живут только хардкодом в Go и не связаны с классами `ptszi_controls`;
- **совместимости** между средствами;
- **времени**: модель полностью статична, понятия «через год» не существует;
- **оптимизации**: нет ни целевой функции, ни ограничений, ни перебора.

Ключевой вывод: **`effectiveness` сейчас вводится руками**. Это число «из головы оператора», а не свойство продукта. Пока оно такое, любая оптимизация будет оптимизировать чужие догадки.

## 2. Разрыв между «есть» и «надо»

Постановка требует различать три уровня, которых модель сейчас не различает:

```
класс меры   (A «Антивирус»)          ← это есть: ptszi_controls
   ↓
продукт      (Kaspersky ES / Dr.Web)  ← этого нет в БД
   ↓
экземпляр    (лицензия на 200 узлов, внедрён на активе X)  ← этого нет
```

Вся текущая модель живёт на верхнем уровне. Стоимость и совместимость существуют на среднем и нижнем. **Это главная структурная работа**: не формулы, а достройка модели вниз.

## 3. Идеи по слоям

### 3.1. Слой продуктов

**Важно: этот слой предусмотрен исходной концепцией.** На структурно-функциональной схеме из презентации блок «Формирование рекомендаций по совершенствованию системы ИБ КС» питается от **БД ПАСЗИ** — базы программно-аппаратных средств защиты информации. То есть в замысле она есть, а в реализации отсутствует: сейчас рекомендации выдаются на уровне классов («антивирусная защита», «средства защиты от НСД», «средства межсетевого экранирования», «средства обнаружения вторжений» — ровно как на последнем слайде), но до конкретных средств не спускаются.

Значит слой продуктов — не надстройка сверх задуманного, а **достройка недостающего блока концепции**. Это удобно для обоснования: мы не меняем модель, а доводим её до вида, заложенного в схеме.

Новая сущность — конкретное средство защиты:

| Поле | Смысл | Откуда брать |
|---|---|---|
| `control_id` | к какому классу относится (A, FW, …) | связь с `ptszi_controls` |
| `name`, `vendor` | идентификация | Минреестр |
| `registry_number` | реестр Минцифры | Минреестр |
| `fstec_class` | класс защиты по ФСТЭК (1–6) | сертификат ФСТЭК |
| `base_effectiveness` | базовая эффективность | экспертно / из класса |
| `capex_license`, `capex_deploy` | закупка и внедрение | см. раздел 6 |
| `opex_yearly` | поддержка, продление | то же |
| `admin_hours_yearly` | трудозатраты на сопровождение | экспертно |
| `deploy_months` | срок внедрения | экспертно |

**Идея, которая мне кажется сильной**: `fstec_class` — это не украшение, а **жёсткое ограничение допустимости**. Для ГИС класса защищённости К1 нельзя брать СЗИ ниже 4 класса. То есть оптимизация идёт не по всему каталогу, а по допустимому подмножеству, и часть продуктов отсекается до всякой экономики. Это связывает выбор с уже реализованным `compliance` и даёт задаче регуляторную осмысленность, а не только «дешевле-дороже».

### 3.2. Модель эффективности комплекса

Сейчас: `resulting_coverage = coverage · effectiveness`, дальше произведение непокрытий. Что предлагаю добавить:

**(а) Насыщение внутри класса.** Два антивируса не дают удвоения — они дают почти ничего сверх первого. Ввести правило: внутри одного класса засчитывается лучший продукт, остальные — с сильно понижающим коэффициентом (или не засчитываются вовсе). Иначе оптимизатор начнёт «набивать» дешёвыми дублями.

**(б) Синергия между классами.** Есть пары, где совместный эффект выше суммы: IDS + централизованное администрирование (есть кому реагировать на алерт), резервное копирование + контроль целостности. Моделировать как поправочный коэффициент на паре классов.

**(в) Антисинергия / конфликты.** Два средства защиты от НСД на одной машине — конфликт драйверов, реальная эксплуатационная проблема. Это не «меньше эффект», это «нельзя ставить вместе» — ограничение, а не штраф.

Формально: таблица совместимости с типом связи `conflict` / `synergy` / `requires`. Тип `requires` тоже нужен — шифрование трафика без инфраструктуры ключей не работает.

### 3.3. Модель стоимости

Минимально осмысленно — разделить на три части, иначе сравнение будет врать:

```
TCO(горизонт) = CAPEX + Σ по годам OPEX_год + Σ по годам (admin_hours · ставка)
```

Третье слагаемое принципиально: дешёвое в закупке средство, требующее выделенного администратора, на трёхлетнем горизонте дороже коробочного. Без него «оптимум» будет систематически смещён в сторону дешёвых и трудоёмких решений. Для диплома это хороший содержательный тезис.

### 3.4. Целевая функция

Тут развилка, и она важная.

**Вариант A — минимизировать остаточный риск при ограниченном бюджете.**
Максимизируем `ΔW` (суммарное снижение по всем парам актив×угроза) при `TCO ≤ бюджет`.
Плюс: работает на тех данных, что есть. Минус: `W` безразмерна, «снизили на 0.3» не переводится в деньги.

**Вариант B — минимизировать полные издержки через денежный ущерб.**
Ввести стоимость ущерба от реализации угрозы, считать ожидаемые годовые потери, минимизировать `потери + затраты`. Отсюда получается метрика окупаемости вложений в защиту — см. раздел 8, там есть готовый индекс RORI с публикациями, если понадобится опора на литературу.
Плюс: экономически честно, сравнимо с бюджетом в тех же единицах, красиво защищается. Минус: нужна оценка ущерба — ещё один слой экспертных данных.

**Моя рекомендация:** делать A как основу (он реализуем на текущих данных), а B — как надстройку с явной пометкой «оценочно». Тогда работа не зависит от того, найдутся ли данные об ущербе.

### 3.5. Алгоритмы выбора

Задача — вариант рюкзака, но с нелинейной ценностью (из-за насыщения) и ограничениями совместимости. Точное решение NP-трудно, но размерность у нас маленькая: 11 классов, продуктов реально десятки.

| Алгоритм | Идея | Плюсы | Минусы |
|---|---|---|---|
| **Жадный по отдаче** | на каждом шаге берём продукт с лучшим отношением «снижение риска / цена» | быстро, объяснимо оператору: «следующий рубль лучше всего потратить сюда» | не гарантирует оптимума |
| **Динамическое программирование** | дискретизировать бюджет, классический рюкзак | точен при линейности | плохо дружит с насыщением и конфликтами |
| **Целочисленное линейное программирование** | сформулировать как ЦЛП, отдать солверу | точный оптимум, ограничения выражаются естественно | нужна линеаризация нелинейного покрытия, внешняя зависимость |
| **Полный перебор** | при малой размерности реально | эталон для проверки остальных | экспоненциален |

**Идея для дипломной ценности:** реализовать жадный как рабочий, полный перебор — как эталон на малых наборах, и **показать на графике, насколько жадный отстаёт от оптимума**. Это готовый раздел с экспериментом, а не просто «я написал алгоритм».

### 3.6. «На дистанции» — самое интересное

Это то, что отличает задачу от обычного рюкзака, и на чём стоит сделать акцент.

Что значит «на дистанции», как я это понимаю:

**(а) Бюджет разбит по периодам.** Нельзя купить всё в первый год. Есть годовой лимит, и вопрос не «что купить», а «что купить **сначала**». Порядок меняет накопленный риск: год под критической угрозой стоит дороже, чем год под средней.

**(б) Целевая функция — площадь под кривой риска, а не конечная точка.** Два плана могут прийти к одному остаточному риску за 3 года, но один снижает его сразу, другой — в последний год. Первый лучше, и метрика должна это видеть:

```
минимизировать Σ по периодам (W(t) · длительность)
```

Это, по-моему, главная содержательная идея всей задачи.

**(в) Задержка внедрения.** Средство, купленное сегодня, начинает защищать через `deploy_months`. Пока внедряется — денег стоит, риск не снижает.

**(г) Дисконтирование.** Рубль через три года дешевле сегодняшнего — стандартный NPV.

**(д) Деградация и обновление.** Эффективность падает со временем (новые угрозы против старых сигнатур), сертификаты истекают, лицензии продлеваются. На горизонте 3–5 лет это заметно.

**(е) Зависимости порядка.** Сегментацию сети логично делать до внедрения IDS. Это ограничения предшествования — превращает выбор в задачу планирования, а не только отбора.

Результат — не список закупок, а **дорожная карта**: что в каком году, при каком годовом бюджете, с какой кривой снижения риска.

## 4. Что показывать в интерфейсе

- **Парето-фронт «стоимость / остаточный риск»**: каждая точка — комплекс, кривая — граница разумного. Наглядно показывает, где деньги перестают давать эффект.
- **Кривая W(t)** для сравниваемых планов — прямое сравнение «быстро, но дорого» против «дёшево, но долго».
- **Дорожная карта по годам** — диаграмма внедрения.
- **Режим «что если»**: убрать средство из плана и увидеть, как поднялся риск. У вас на `RiskGraphPage` уже есть клиентский what-if — логика та же.

## 5. Развилки, где нужно твоё решение

1. **Целевая функция**: A (риск при бюджете) или A+B (через денежный ущерб и ROSI)?
2. **«Класс»** в постановке — я понял как категорию средств (антивирусы, МЭ). Если имелся в виду класс защиты ФСТЭК (1–6) — акцент сместится на допустимость по требованиям, а не на сравнение продуктов внутри категории. Уточни.
3. **Горизонт**: 3 года или 5? От этого зависит, нужна ли деградация эффективности.
4. **Глубина совместимости**: только конфликты (просто, честно) или ещё синергия (богаче, но коэффициенты будут взяты с потолка)?

## 6. Риски, о которых стоит сказать прямо

**Главный: откуда брать цены.** Систематизированных данных о стоимости российских СЗИ в открытом доступе нет. Минреестр цен не содержит — я проверил структуру базы, там их нет. Варианты:

- **Ручной справочник** — честно, но данные придётся собирать самому и защищать их происхождение.
- **Госзакупки** (zakupki.gov.ru) — там есть реальные цены контрактов на СЗИ. Технически это открытые данные, и как источник для дипломной работы выглядит defensible. Но парсинг — отдельная работа, и цены там за конкретные поставки с разными объёмами лицензий, сопоставимость хромает.
- **Экспертные диапазоны** — «от/до» вместо точных чисел, и оптимизация по диапазонам. Слабее, но честнее, чем выдуманная точность.

Рекомендую заложить в модель то, что цена — **оценка с диапазоном**, а не точное число. Тогда результат честно выглядит как «этот план дешевле того при любых разумных ценах» вместо ложной точности до рубля.

**Второй: коэффициенты берутся из воздуха.** `coverage` в матрице, синергия, деградация — всё экспертные оценки. Это нормально для такой модели, но требует **анализа чувствительности**: показать, что выбранный комплекс не разваливается при изменении коэффициентов на ±20%. Без этого любой вопрос «а почему 0.75?» обрушивает защиту работы. С этим — превращается в раздел «устойчивость решения».

**Третий, технический: в проекте две параллельные модели мер защиты.**
`controls` / `asset_controls` (с `reduces_likelihood_by`, `reduces_impact_by`) из `001_init` — и `ptszi_controls` / `asset_ptszi_controls` из `014`. Плюс `vl_category_controls` в ветке. Они не связаны между собой.

Решено: существующее не переделываем. Тогда новый слой продуктов цепляется **к ПТСЗИ-модели** (`ptszi_controls`), потому что именно на ней стоит расчёт `W` и матрица «звено × мера». Старая `controls` остаётся жить своей жизнью и в оптимизации не участвует. Практическое следствие: в UI появятся две несвязанные сущности «меры защиты» — это цена решения не трогать существующее, и о ней стоит помнить при демонстрации.

Отдельно: ветка `feat/risk-graph-viz` (PR #5) содержит миграции 020–040 и сервисы `control` / `compliance` / `organization`, которых нет в `main`. Новые миграции нумеруем с запасом (от `050`), чтобы не столкнуться с ними при слиянии.

## 7. Возможный порядок работ

Существующий код и модель не трогаем — всё только достраивается сверху. Порядок такой, чтобы на каждом этапе было что показать:

1. **Слой продуктов** — таблица СЗИ, привязка к классам `ptszi_controls`, наполнение из Минреестра. Пока без цен: уже даёт «какие конкретно средства закрывают это звено».
2. **Стоимость** — CAPEX / OPEX / трудозатраты, TCO на горизонте. Появляется сравнение вариантов.
3. **Совместимость** — конфликты и требования как ограничения.
4. **Статическая оптимизация** — жадный + эталонный перебор, Парето-фронт. Это уже отвечает на пункт 1 постановки целиком.
5. **Временное измерение** — периоды, задержки внедрения, площадь под кривой риска, дорожная карта. Это пункт 2.
6. **Анализ чувствительности** — устойчивость к коэффициентам.

Пункты 1–4 дают законченный результат сами по себе. 5 — то, ради чего задача формулировалась.

Ничего из этого не требует правок в `Q_reaction`, формуле `W` или существующих таблицах: оптимизатор вызывает уже написанный расчёт как чёрный ящик, перебирая варианты состава мер.

### Правило достоверности

Сборщик **отбрасывает строку с ценой, но без ссылки на источник**. Цифра, происхождение которой нечем подтвердить, для защищаемой работы хуже, чем честно отсутствующая. Каждая цена несёт `source_url`, тип источника, дату сбора и пояснение, за какую конфигурацию она.

Не засчитаны четыре цифры, которые светились в поиске, но не открывались прямой проверкой: 647 916 ₽ за Eltex ESR-20 (антибот), 250–300 тыс. за Security Capsule SIEM (на страницах вендора таких сумм нет), 120 000 за Dionis-NX (домен не резолвится), 151 407 и 212 409 за Diamond VPN/FW.

### Почему у 102 позиций цены нет

Это свойство рынка, а не пробел сбора. **Публичный прайс существует только там, где у продукта фиксированная единица лицензирования**: рабочее место, коробка, соединение, шасси. Корпоративные СЗИ — NGFW, SIEM, DLP, NDR, WAF — лицензируются по метрикам нагрузки: RPS, EPS, объём трафика, сокеты, терабайты в сутки. Списочной цены у них быть не может, и все проверенные площадки отвечают «цена по запросу»: Positive Technologies, С-Терра, Гарда, InfoWatch, R-Vision, RuSIEM, BI.ZONE, Solar, Zecurion, СёрчИнформ.

Для работы это означает простую вещь: **оптимизация возможна в сегменте средств с фиксированной единицей лицензирования и невозможна в сегменте проектных поставок**. Это ограничение стоит заявить в работе прямо — оно содержательное, а не техническое.

Неиспробованным остался один источник — **госзакупки**. Цены контрактов на те же Positive и С-Терра публикуются в ЕИС и индексируются агрегаторами; проверка показала, что данные там есть. Это способ получить цифры для проектного сегмента, но с оговоркой: цена контракта отражает конкретную поставку с конкретным объёмом, а не прайс, поэтому без количества единиц такая цифра бесполезна.

### Что осталось незакрытым

- **`TE` и `DS`** — криптосредства сертифицирует ФСБ, а не ФСТЭК; в реестре их по два. Закрывается другим реестром.
- **`HP` и `DD`** — у ФСТЭК нет отдельных профилей для honeypot и подавления DDoS, как класс они не выделены.
- **Класс `AD` раздут**: он самый большой (106) в основном потому, что маппинг относит туда все ОС, СУБД и средства виртуализации. Для «систем администрирования» это натяжка, и оптимизатор будет считать, что выбор там шире, чем он есть. Правится одной строкой в `PTSZI_CONTROL_MAP` сборщика, если решим выносить платформы в отдельный тип.

### Интеграция в CyberRisk

Каталог доступен через `GET /api/external/szi/certificates` (фильтры: метод ПТСЗИ, класс защиты, только действующие) и `GET /api/external/szi/coverage`. Цены отдаются вместе с сертификатом — вместе с источником, чтобы происхождение цифры не терялось.

Сводка покрытия показывает `with_price` рядом с числом сертификатов: сразу видно, где подбор возможен, а где выбирать не из чего.

## 7-тер. Оптимизатор — сделано

### Принятые решения

**Целевая функция — вариант A**: максимальное снижение суммарного `W` по применимым угрозам актива при ограниченном бюджете. Денежная оценка ущерба не используется: её пришлось бы брать экспертно, а `W` уже считается моделью на реальных данных БДУ. Вариант B остаётся возможным расширением, но работа от него не зависит.

Суммой, а не средним по угрозам: добавление меры не должно «размываться» числом сценариев.

**Класс `AD` очищен**: ОС, СУБД и средства виртуализации больше не отображаются на методы противодействия. `AD` сжался со 106 позиций до 45 — теперь это действительно системы администрирования, а не платформы.

### Что реализовано

Пакет `internal/service/optimizer`, эндпоинт `GET /api/ptszi/assets/:assetID/optimize?budget=...&max_class=...`.

Расчёт `W` **не переопределяется**: оптимизатор вызывает ту же `ptszi.CalculateW` и повторяет ту же мультипликативную модель покрытия, просто применяя их к гипотетическим наборам мер. Существующий код не тронут.

**Два алгоритма:**

- **Жадный** — на каждом шаге берёт меру с лучшим отношением снижения риска к стоимости. Объясним оператору: «следующий рубль лучше всего потратить сюда».
- **Полный перебор** — эталон до 18 кандидатов. Нужен, чтобы измерить отставание жадного, а не надеяться на него. Методов всего 11, так что проверка не теоретическая: она реально выполняется на каждом запросе.

Ответ содержит `greedy_is_optimal` и `exhaustive_delta` — видно, совпал ли жадный план с точным оптимумом.

**Класс защиты ФСТЭК как ограничение допустимости** реализован параметром `max_class`: средства ниже требуемого класса отсекаются до всякой экономики.

### Проверка на реальных данных

Сценарий с четырьмя незакрытыми методами, бюджет 1 млн:

```
baseline W = 0.8333 → 0.5068   (снижение 39.2%)
потрачено 14 085 ₽ из 1 000 000

1. A    Dr.Web Mobile Security Suite        674 ₽   ΔW=0.2133
2. L    Ревизор 1 ХР                      1 420 ₽   ΔW=0.0672
3. IDS  Kaspersky EDR                     4 491 ₽   ΔW=0.0317
4. FW   Dallas Lock 8.0-K                 7 500 ₽   ΔW=0.0144

сверка с перебором: оптимум 0.3266, жадный 0.3266, совпадение
```

Убывание `ΔW` по шагам — прямое следствие мультипликативной модели: каждая следующая мера добавляет лишь то, что пропустили предыдущие.

### Честное ограничение, которое видно на этом же примере

В плане соседствуют мобильный антивирус за 674 ₽ и СЗИ от НСД за 7 500 ₽ — **это цены за разные единицы**: одно устройство против рабочей станции. Оптимизатор сравнивает их напрямую и охотно берёт формально дешёвое, хотя для защиты сервера мобильная лицензия не годится.

Привести цены к общей единице нельзя, пока в модели нет **масштаба актива** — числа рабочих мест, серверов и каналов связи. Поэтому план читается как «минимальная цена закрытия метода», а не как готовая смета, и API возвращает об этом явное предупреждение в поле `warnings`.

Это следующий естественный шаг: добавить активу масштаб, и стоимость станет считаться по-настоящему.

### Чего пока нет

- **Совместимость** (конфликты, синергия, зависимости) — модель есть в разделе 3.2, в коде нет.
- **Временное измерение** — площадь под кривой риска, периоды, задержки внедрения. Это второй пункт постановки и главная незанятая ниша по обзору из раздела 8.
- **Анализ чувствительности** — устойчивость плана к изменению коэффициентов.

## 8. Обзор: что уже сделано в мире

Поискал на GitHub, прежде чем предлагать своё. Главное — прямого аналога нет, но есть две работы, из которых стоит взять готовое.

### RORI — метрика, специально созданная для выбора контрмер

[ozgunbal/countermeasure-selection-tool](https://github.com/ozgunbal/countermeasure-selection-tool) реализует индекс RORI (Return On Response Investment) из работ Gonzalez-Granadillo:

```
RORI = ((ALE · RM) − ARC) / (ARC + AIV) · 100
```

| Обозначение | Смысл |
|---|---|
| `ALE` | ожидаемые годовые потери от атаки |
| `RM` | снижение риска этой контрмерой (0–1) |
| `ARC` | годовая стоимость контрмеры |
| `AIV` | годовая стоимость защищаемой инфраструктуры |

В отличие от самодельного ROSI, RORI нормирован на стоимость инфраструктуры — сравним между системами разного масштаба, и под него есть публикации для ссылок. Держим как опцию для варианта B из раздела 3.4.

Ещё оттуда можно взять:

- **Комбинации считаются через объединение покрытий**, а не сумму — в их коде это `volumeUnion`. В roadmap проекта висит признанный баг «UNION is calculated wrong» — то есть двойной счёт покрытия. Это ровно та проблема, которую в нашей модели уже решает произведение непокрытий в `Q_reaction`.
- **Эффективность комбинации = минимум из эффективностей** входящих средств. Консервативная оценка: комплекс не крепче слабейшего звена. Как альтернатива моей идее насыщения — проще и защищается легче.
- Полный перебор подмножеств контрмер (`getCombinations`) — при их размерности это работает, что подтверждает: эталонный перебор реалистичен.

### Генетический алгоритм для размещения мер

[sekagard/GA-Based-Attack-Graph-Optimization](https://github.com/sekagard/GA-Based-Attack-Graph-Optimization---Defensive-Control-Placement) — целевая функция:

```python
p = base_prob
for i in chosen:
    p *= (1.0 - reduction_i)      # мультипликативное снижение
residual_risk += p * impact

fitness = risk_reduction − λ·cost − penalty(превышение бюджета)
```

**Это в точности наша математика** — та же мультипликативная модель, что в `Q_reaction`. Хорошая новость: фундамент, который уже есть в проекте, совпадает с тем, как задачу решают в подобных работах, и его не надо переделывать.

Что берём: бюджет как мягкое ограничение со штрафом за превышение (позволяет алгоритму исследовать пограничные решения), и `λ·cost` в целевой функции как явный обмен «риск против денег».

### Смежное

- **MITRE D3FEND** — матрица защитных техник, маппинг «контрмера ↔ техника атаки». Альтернативный источник связей, но у нас своя матрица VL×мера из диплома, и она ближе к российской специфике.
- **Российские проекты**: [TartarugZ/ThreatModel](https://github.com/TartarugZ/ThreatModel) (модель угроз по методике ФСТЭК), [dedvmedved-dot/fstek-attestation](https://github.com/dedvmedved-dot/fstek-attestation) (подготовка к аттестации). Соседи по теме, но оптимизацией выбора не занимаются.
- **Данных о ценах не нашлось.** Ни готовых датасетов по стоимости СЗИ, ни рабочих парсеров госзакупок под эту задачу. Это подтверждает риск из раздела 6 — источник цен придётся делать самому.

### Чего нет ни у кого — и это наша новизна

| Аспект | RORI-инструмент | GA-проект | Наша задача |
|---|---|---|---|
| Стоимость | ARC | простая cost | CAPEX + OPEX + трудозатраты |
| Совместимость средств | нет | нет | конфликты / синергия / зависимости |
| **Время, дистанция** | **нет** | **нет** | **периоды, задержки, площадь под кривой** |
| Регуляторные ограничения | нет | нет | класс ФСТЭК как допустимость |
| Конкретные продукты | абстрактные меры | абстрактные меры | Минреестр, сертификаты |

Оба найденных решения **статические**: выбирают комплекс на один момент. Временного измерения нет ни в одном. Это и есть незанятое место — и, что удобно, именно второй пункт твоей постановки.

## Что мне кажется самым ценным

Если убрать всё лишнее, три идеи, ради которых стоит это делать:

1. **Минимизировать площадь под кривой риска, а не конечный риск** — тогда «на дистанции» получает точный смысл, и порядок внедрения начинает влиять на ответ. Обзор в разделе 8 показал, что временного измерения нет ни в одном из найденных решений — это незанятое место.
2. **Класс защиты ФСТЭК как ограничение допустимости** — связывает оптимизацию с регуляторикой, отсекает недопустимое до экономики.
3. **Учёт трудозатрат в TCO** — показывает неочевидное: дешёвое в закупке решение может быть дороже на горизонте.

И приятный вывод из обзора: мультипликативная модель покрытия, которая **уже реализована** в `Q_reaction`, совпадает с тем, как считают в найденных работах. Фундамент переделывать не нужно — только достраивать.
